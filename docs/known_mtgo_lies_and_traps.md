# Known MTGO Lies and Traps

False assumptions and dangerous patterns when working with MTGO's local files. These are properties of MTGO itself, not bugs in this app. Every parser, classifier and projection rule must treat them as normal.

Carried over from the 0.x app (its `docs/known_mtgo_lies_and_traps.md`), translated for v1, and extended with what was learned while designing the Rust port.

---

## Prime directive

> **Logs are hostile input.**
> Trust structure, not semantics.
> Trust invariants, not messages.
> Trust pipelines, not appearances.

Any code working with MTGO data must assume malformed input, partial state, missing events, duplicate events, reprocessing, and corrupted sequences. If logic requires clean MTGO behaviour to work, the logic is wrong.

---

## 1. "Match ended" does not mean the match ended

MTGO may emit a match-end style message, close the game client, or stop logging abruptly, all without a clean game-end event, a clean match-complete event, or a winner.

**Rule:** match completion is inferred, never trusted. v1 completes a match only on a completion signal or through the finalize rules (spec section 5.5).

## 2. "Game over" does not mean the winner is known

Games end through client crashes, disconnects, window closes, network loss and soft crashes, often with no life total at zero, no concede, and no winner line.

**Rule:** a game result can be win, loss, or unknown. Unknown is a valid stored answer.

## 3. Logs lie about order

Buffered writes, delayed flushes, batched JSON and interleaved meta events mean line order and timestamps do not reliably reflect real time.

**Rule:** never rely on timestamps for causality. Within a match, v1 orders events by `(file_id, byte_offset)`.

**Risk, not yet seen in real logs:** the gap scan that settles a quiet match (section 13) walks events in key order and trusts each event's time. If a real log shows times out of order inside a match, the gap can be mis-measured (#86 D3). Add a fixture and harden the scan then.

## 4. Duplicate events are normal

MTGO re-emits state updates, headers, status messages and JSON blocks.

**Rule:** processing is idempotent. The same event applied twice changes nothing.

## 5. Most JSON is noise

Many JSON blocks are UI telemetry, Twitch info, client metadata or analytics.

**Rule:** whitelist the line types that matter; ignore everything else by default.

## 6. Context switches mid-stream

The log jumps between matches, interleaves league data, emits stale match headers and re-references old matches. It also logs state changes for **other players' matches** seen in lobbies (hundreds per session: `MatchNotJoined...`, `TournamentMatchUninitializedState -> TournamentMatchClosedState`).

**Rule:** attribute events by explicit identifiers (match token, Match ID, Game ID), never by proximity. A match only exists once the local player has joined it.

## 7. The local player is not always explicit

The local player may be absent from early headers and appear only in later events. MTGO's daily log rotation opens a new file **without** re-logging the Login line.

**Rule:** local identity resolves in priority order:
1. The `(Login|MtGO Login Success) Username: X (id)` line, carried across rotation.
2. The `Username: X Deck Used in Game ID: N` line for that game.
3. A single known account among the match's players.

Only the `MtGO Login Success` context counts. `MtGO Login Last Success`, `(UI|LastLoginName) Username=`, and Twitch lines all contain usernames too and must not be treated as a login.

## 8. Deck state drifts

Deck files update mid-session, get overwritten, duplicate across directories, and disappear and reappear.

**Rule:** use the latest timestamp, version every change, and never assume a deck file persists.

## 9. File systems lie

Logs rotate, truncate, get replaced in place, change identity under the same name, and shrink.

**Rule:** a filename is not a file identity. Identity is the first 4KB hash, the true creation time, and an anchor hash. On Linux, `ctime` is the inode-change time and moves on every write, so it must never be used as a creation time.

- **MTGO rewrites `mtgo.log` in place each time it starts, and Windows keeps the old creation time** (verified on Windows, 2026-10-07, #48). A log created on 30/09 held only that day's session from 16:17 on 07/10; another, created on 24/09, held a session from 29/09. The creation time therefore never dates a file: v1 works a new file's day anchor back from its last write (spec 5.4 rule 1). The rewrite is detected as a rotation because the file shrinks or its head changes; `created_forward` does not fire for it.

## 10. Silence is not state

No new log lines may mean MTGO froze, crashed, paused logging, or the user alt-tabbed.

**Rule:** absence of evidence is not evidence of completion. v1 only resolves a silent match after 60 minutes. A match with no end signal and no decided score is abandoned then, and a later event still revives it. A match that ended or was decided is completed (see "MTGO sometimes never logs a match completion" below), and a quiet completion never goes back to an earlier state.

## 11. MTGO is not deterministic

The same actions produce different log shapes across sessions. MTGO logging is not a stable API.

**Rule:** parse heuristically, tolerantly and defensively. Every new log shape becomes a fixture.

## 12. There are no clean boundaries

No clean match start, game start, game end, or match end is guaranteed.

**Rule:** everything is inferred state, not declared truth.

## 13. MTGO sometimes never logs a match completion

A match can end, or be decided on the score, and MTGO never writes the completion signal (issue #26). Waiting for the signal would leave the match open forever.

**Rule:** an ended or decided match with no completion signal is completed after a 60-minute gap in the log (`Resolution::Quiet`). The result settles on the facts from before the gap, and the match keeps that state and outcome whatever arrives later, a completion signal or a lost connection included (spec 5.5, the earliest settlement wins).

## 14. Two clients mean two current accounts

Two MTGO clients on two accounts write two `mtgo.log` files at once, and each logs its own Login line. There is no "the" logged-in account: the newest Login only says which client was started last.

**Rule:** a match belongs to the account in its own game state (the local seat), never to the current account, so both clients' matches are built (0.x `AdvanceMatchStateTest` "creates a match for a known account even when a different account is active"). The current account only chooses which account's data the pages show: the newer of the user's last switch from the header and the newest Login line of a tracked account, compared by time (release spec 5). A switch holds until the next Login; a Login from either client takes over. Login times are log times, switch times wall clock; both are UTC unix milliseconds.

## 0.x data quirks (for the importer)

The 0.x database is not MTGO, but it is hostile input of its own (verified on the owner's 0.x database, 2026-10-07):
- **Not every token is MTGO's.** Matches 0.x imported from MTGO's game history, and manual matches, have a random UUID as `token`. A history-imported match keeps the real MTGO match ID in `mtgo_id`, so v1 deduplicates against live rows by match ID as well as by token. Manual matches have `mtgo_id` `manual_<random>`.
- **History-imported times may be local.** 0.x parsed MTGO's game-history timestamps without a zone, so those `started_at` values may be local time stored as if UTC. v1 copies them as they are.
- **`on_play` defaults to 0.** The column is `NOT NULL DEFAULT 0`, so a game whose play/draw was never seen reads as "on the draw" (6 of 837 games in the owner's database). v1 keeps 0.x's reading, which its stats also used.
- **`outcome` is NULL until a match completes**, and `result` is a dead legacy column. `games.won` is NULL when the game's winner is unknown.
- **Not unique where it looks unique.** `matches.token`, `matches.mtgo_id` and `players.username` have no unique index. The same MTGO match can be in 0.x twice (a log capture and a history import: different tokens, the same `mtgo_id`); the import keeps the first row by id and counts the later one as a duplicate.
- **Matches without a local seat.** Some matches have no games, or games with no `is_local = 1` player row (5 of 476 in the owner's database); there is no account to give them, so the import skips them.
- **Frame times come in three shapes.** 0.x `game_timelines.timestamp` holds `Y-m-d H:i:s` in older rows (43,075 of 45,293 in the owner's database, game ids up to 5422), `HH:MM:SS` (1,809) and `HH:MM:SS.mmm` from the dense recorder (409, game ids from 5424). The dated shape is MTGO's local clock on the day the row was written, not a UTC instant. v1 keeps the time of day only (`replay::normalise_time`, replays spec ruling 5); a match bundle dates a time-of-day frame on the local day of the game's end, a day earlier when that lands more than 12 hours after the end (0.x `frameInstant`).
- **Partial live data can replace complete history games (#180).** When a history import and a live capture name the same match, live wins. A live capture that saw only part of the match (v1 started mid-match, or the log was cut) can replace games the history record held in full, so the stored match has fewer games than MTGO played. v1 keeps 0.x's rule and does not merge the two.
- **The server stores a shared replay as sent.** mymtgo.com validates a desktop upload but never redacts it, so an opponent's name that survives on the client is public. v1 redacts every frame `Name` and log line and runs `assert_gone` before any request body is built (`prepare_shared_snapshot`); a name glued to other text that the whole-token rule cannot replace refuses the share instead.
- **The packaged database is not `nativephp.sqlite`.** An installed 0.x keeps its database at `<userData>/database/database.sqlite`; `nativephp.sqlite` is only the development copy. Detection tries `database.sqlite` first, then `nativephp.sqlite`, for `mymtgo` then `com.mymtgo.app` (release spec section 13 item 1).
- **0.x and v1 both make "MyMTGO" shortcuts.** 0.x's electron-builder installer writes Start menu and desktop shortcuts for its product, and v1's look the same, so with both installed the user cannot tell them apart and one install can replace the other's link. v1's installer offers to remove 0.x before it writes its own shortcuts (`app/installer/hooks.nsh`).
- **0.x's uninstall entry is lower case and keyed by a GUID.** electron-builder writes `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\<GUID>` with `DisplayName` `mymtgo` and `UninstallString` `"<folder>\Uninstall mymtgo.exe" /currentuser`. NSIS string compares are case insensitive by default, so the hook compares with `S==`: v1's own entry ("MyMTGO") must never match. An NSIS uninstaller started without `_?=<folder>` copies itself to TEMP and returns at once, so `ExecWait` would not wait; with `_?=` it runs in place and leaves its own file behind. Silent uninstalls never get `--delete-app-data`, and 0.x was built with `deleteAppDataOnUninstall` false, so `%APPDATA%\mymtgo` (the database the import reads) stays.
- **The installer's migration answer is a file v1 reads once.** A Tauri NSIS hooks file cannot add a wizard page, so the "migrate or start fresh" question is a Yes/No `MessageBox` in `NSIS_HOOK_PREINSTALL`, asked only when the install is interactive (not `/S`, `/P` or `/UPDATE`), v1 has no `%APPDATA%\com.mymtgo.desktop\mymtgo.sqlite` yet, and a 0.x `database.sqlite` exists. The answer is written in `NSIS_HOOK_POSTINSTALL` (so a cancelled or failed install leaves none) as one word to `%APPDATA%\com.mymtgo.desktop\first-run-choice.txt`. v1 deletes that file at every start whatever it says (a stale, unreadable or unknown file is never acted on twice), and saves the answer as `first_run_choice`; a saved answer or any v1 match means it is never asked again. The installer only checks the 0.x file exists (`IfFileExists`), it never opens it: the import runs in v1, with progress, retry and the tracker as the only writer.
- **An elevated installer sees another user's folders.** The install mode is `currentUser`, so `$APPDATA` is the roaming folder of whoever runs the installer. Started "as administrator" under a different account, it looks for 0.x data and writes the choice file in that account's folders, not the player's. v1 then finds no file for the player and, when it detects 0.x data, asks the same question in the app.
- **Renaming the product moves everything but the data.** Tauri names the install folder (`%LOCALAPPDATA%\<productName>`), the uninstall entry, the shortcuts, the Run value and the Linux autostart entry (`~/.config/autostart/<productName>.desktop`) after `productName`, but the data folder after the identifier, so "MyMTGO Beta" and "MyMTGO" share `%APPDATA%\com.mymtgo.desktop` and nothing needs copying. A first install under the new name is a fresh install beside the old one, not an update, so the post-install hook removes the old one (release spec 13.1). Tauri 2.12's uninstaller deletes its own Run value when not run with `/UPDATE`, so the hook reads it before running the old uninstaller. The uninstaller deletes the data folder only when the confirm page's "Delete the application data" box was ticked (`$DeleteAppDataCheckboxState`, set in `un.ConfirmLeave`); a silent run skips every page and no command line option sets it.
- **0.x's launch at login is not in the kept settings.** settings.json's `autostart_enabled` is an OS duplicate the importer drops; the import reads it on its own, PHP's `(bool)` cast (`"0"`, `""`, `0`, `null` are off), and turns v1's launch at login on once, only while `autostart_from_0x_applied` is false (any change of v1's switch sets it).

## The log format itself

- **Lines carry no date.** Every header is `HH:MM:SS [LVL] (Category|Context)`. Dates are reconstructed from a per-file day anchor and timezone, rolling the date forward when the time of day wraps around midnight. Never date a catch-up read from the file's modified time: catching up a file that spans midnight would misdate half of it (0.x does this, see `ConvertMtgoTimestamp`). A silent gap of 12 to 24 hours (client left open overnight) fools the rollover rule, because 08:00 followed by 07:00 the next day looks like a small step back; live reads therefore cross-check the date against their read time (spec 5.4). The same gap inside a backlog caught up later is still undetectable. Local times are wall-clock times, so a time the clocks skip moves on by the real length of the gap (half an hour on Lord Howe Island, not a fixed hour) and a repeated time takes the earlier instant, as PHP reads them; every local time goes through `mtgo_protocol::local_to_utc_ms`.
- **One bad live time moves the date (risk, not yet seen in real logs).** The live cross-check trusts each live line's time of day. A single live line whose time of day is wrong by more than 12 hours (a clock change, a corrupt or stale header) re-anchors the running date to its read time, and that line's time also becomes the clock's "last" time, so the next line can roll the date forward wrongly. Later live lines re-anchor again, but anything dated in between, and the clock state saved for a restart, can be a day off. This is 0.x's rule, kept for parity (`DayClock::resolve_live`). If a real log shows it, add a fixture and harden the rule.
- **Events span many lines.** A gameplay event is a header line plus about 15 continuation lines (the key-value block). The last event in the file may still be mid-write, so it is provisional until the next header arrives or the file has been quiet for a moment.
- **Error lines can be data.** `FlsBoosterDraftOpenPackMessage` is logged at `[ERR]` as "Handler Not Registered" and carries the pack round.
- **Lines can be huge.** `EventSyncData_t` tournament lines reach about 1MB.

## MetaMessage byte arrays carry the gameplay stream

`game_management_json` lines carry a `MetaMessage` byte array with every gameplay event needed for live match resolution and card stats: rolls, joins, play/draw choices, starting hands, casts, wins, concedes, disconnects, and match score lines.

- **Every `game_management_json` event carries `MatchToken`, `MatchID` and `GameID`** (verified on all fixtures). Games are keyed by Game ID.
- **Other event kinds carry only some identifiers.** `match_state_changed` has only the match token. `game_state_update` has only Match ID and Game ID. `deck_used` has only the Game ID. They are linked through the identifiers the gameplay events carry.
- **The key-value block after `Receiver:`** supplies `PlayFormatCd`, `GameStructureCd` (note the space: `GameStructureCd= Modern`), `Description` (tournament id and round as `Tournament:X Round:Y`), and `League Token`.
- **The post-match "X wins the match N-M" line is not in the live stream.** It exists only in the post-match `Match_GameLog_*.dat` file. Live resolution uses per-game results, "leads the match" score lines, and completion state changes.
- **MetaMessage and `.dat` framing differ.** Both use the same GsMessage wire format, but each MetaMessage is one length-prefixed message while the `.dat` body concatenates messages without the prefix.
- **Player names inside MetaMessages are length-framed.** Renaming a player to a name of a different length corrupts the payload. Anonymised fixtures must use same-byte-length fakes.
- **A disconnect is not a result.** "has lost connection to the game" never decides a game or a match while it is active; the player may reconnect.
- **A match left at a level score is not a draw, and the live log says "Match Tied".** When a player drops after evening the score (seen: the opponent conceded game 2 to make it 1-1, then "has lost connection to the game", then "Match Tied 1-1"), MTGO gives the match to the player who stayed, but the "wins the match" line is not in the live log. MTGO's game history agrees: of 671 matches in the owner's history, all 22 that ended 1-1 after two games have a match winner, and the only level-score matches without a winner played three games. A completed level score therefore goes to the player who stayed when a lost connection follows the last "wins the game" with no new game starting, and is a loss when the local player conceded and left (`mtgo_match::derive`). Only the opponent's drop has been seen in a real log; the exact state changes around it are not yet captured as a fixture. The tracker also checks every stored log match against the history once MTGO writes it, and MTGO's verdict wins (`matches.history_outcome`, #454).
- **A mulligan changes the "begins the game" phrase.** After a London mulligan the line is "@PName puts a card on the bottom of their library and begins the game with six cards in hand." Player names may contain spaces, so a greedy name pattern swallows the whole bottoming clause and the hand belongs to nobody. Match the name lazily and allow the optional clause (0.x `ExtractGameResults.php:250` has the greedy form).

## State changes

- The line is `Match State Changed for <token> from <State> to <State>`. Signal names appear in both the from-state and the to-state, so match signals against the **to-state**.
- 0.x used three different, inconsistent lists of end signals. v1 uses one canonical list (spec section 5.5).
- The local concede-and-leave is `...ConcedeReqState` to `...NotJoined...`, for both casual (`MatchConcedeReqState`) and league (`LeagueMatchConcedeReqState`) matches.
- **The sideboarding transition shares a second with the game end.** `... to MatchJoinedSideboardingState` (casual, `League...` and `Tournament...` prefixes) is logged in the same second the game ends, and can come before the game's last game log line, so its time is not after the game's `ended_at`. 0.x anchored on the newest game's `started_at` for that reason. v1 compares log positions: sideboarding is a transition into a `*SideboardingState` after the newest game's first state frame, in `(file_id, byte_offset)` order (overlay spec 7.7).
- **The sideboarding exit shares a second with the next game's first state.** `from ...SideboardingState to ...` is logged in the same second as the next game's first `Game Play Status Update`, so by time it can look like it happened during that game. Match only the **to-state** (`\bto \w*SideboardingState\b`), never a mention of the state, and order by log position.

## Classification order

Tournament and draft markers must be checked **before** the generic `game_management_json` check. Their payloads nest a `MatchCreateInfo.MatchToken` that would otherwise be misread as gameplay.

## Deck lists in the log

- **`deck_used` is per game and can repeat.** `(Twitch Info|Username: X Deck Used in Game ID: N) [{"CatalogId":...}]` is logged at the start of each game, often twice. Take the first. Only game 1's list is the deck as edited; later games' lists are sideboarded.
- **Game 1 can have no `deck_used` line** (0.x logs "no deck_used event for first game"). Never treat game 2's list as the pre-sideboard list.
- **The registered list comes at sideboarding, not at join.** `(BaseClient|Inbound: FlsMatchDeckGetRespMessage) {"MatchToken":...,"MatchID":...,"Cards":[{"CatalogID":...,"Quantity":...,"InSideboard":...}]}` is logged just before `Begin Sideboarding Phase`, so only in matches with a game 2. The first one equals game 1's `deck_used` list (verified on `draft_hobbit` and `league_join_drop`). A later one can group rows differently (one row fewer in `draft_hobbit`) while keeping every card's total.
- **A late login gives game 1 a `[NULL]` list.** When MTGO logs in after a tournament round has started (it reconnects straight into game 1), game 1's line is `(Twitch Info|Username: X Deck Used in Game ID: N) [NULL]`, so no list exists until sideboarding. At that login MTGO logs the tournament's registered deck instead: `(Game Management|Processing Registered Handler for FlsTournamentDeckRespMessage in TournamentJoinedRoundInProgressState) ... Message: {"TournamentToken":...,"TournamentID":N,"DeckCards":[{"CatalogID":...,"Quantity":...,"InSideboard":...}],"DeckName":...,"DeckBoxID":...,"ReturnCode":0}`, with a `} Receiver: ...Tournament` tail on the next lines. `TournamentID` is the match's `tournament_event_id` (`Description=Tournament:N Round:R`), and MTGO locks the list for the whole event, so it is as good as game 1's list. v1 stores it as `match_deck_registered` with a tournament token and no match token. For a tournament that has already finished MTGO answers with an empty list (`"DeckCards":[]`, `"DeckName":""`, `"ReturnCode":2`), which must never be used.
- **Sideboarding keeps totals.** Cards move between main and sideboard, but each catalog id's main plus side quantity stays the same, so a later game's list can only be matched by those totals.
- **Compaction hides the lists.** About 10 minutes after a match ends its events, `deck_used` and the registered list included, move into the match archive. A later relink must read the archive.
- **Limited reads the registered list more loosely than live deck tracking.** 0.x `ReadRegisteredDeck` decodes the payload with `RepairJson` (a cut-short line still reads), treats a row without `InSideboard` as a main deck card, and casts `CatalogID` and `Quantity` as PHP `(int)`. Limited uses its own reader with those rules (`store::limited`); `decks::parse_registered_deck`, which the live deck links use, stays strict. Quantities are clamped to 250 and rows with none dropped, so hostile numbers cannot overflow the pool sums.
- **The newest registered list may not read.** 0.x took the newest `match_deck_registered` event and gave no deck when it did not read (or had no cards). v1 takes the newest one that reads, on purpose: a broken newest line falls back to the previous list rather than losing the match's deck. A parity difference only on a line even `RepairJson` cannot mend.

## Draft leagues

- `FlsBoosterDraftPendingPickMessage` JSON is missing its outer closing brace on every line, and tournament round-info JSON is sometimes truncated. Extract identifiers (the draft token at classification) with targeted patterns. Draft payload fields are decoded with 0.x's `RepairJson` rule (`crates/limited/src/payload.rs`): decode, then retry with up to three missing closing brackets from the text's own bracket balance.
- `OwningLogingID` is MTGO's spelling inside `BoosterInfo`. Match it as-is.
- `Deck Used in Game ID` uses `CatalogId`; every other payload uses `CatalogID`.
- `GameStructureCd= HOBx3` has a space after `=`. Match with `\s*`.
- Draft lines carry no date. Absolute times come from `EndTime`, `Time` and `StartDate` inside the JSON (with a `+01:00` style offset); the line prefix only orders events.
- `LeagueStanding_t` fires once, at draft start, with `MatchWins: 0`. It is not a standings feed. Win/loss comes from match projection.
- `Deck Used` for game 2 can equal game 1 even after `FlsGameSubmitSideboardMessage`. The game state zone snapshot is the post-sideboard truth.
- A finished draft with a built deck and zero matches is normal. Draft completeness and league completeness are independent.
- Re-entering the same league produces a new `CourseID` and `DraftToken` under the same `LeagueID`. Key league runs on `(event_id, mtgo_course_id)`.
- A league has no name in the log. The details panel gives `EventToken`, `EventId`, `Description` (a rules blurb such as `Play up to 5 rounds with your Modern deck...`), `FormatDescription`, `PlayFormatCd` and `GameStructureCd`; leagues get no `EventSyncData_t` line (tournaments' source of names like `Modern Challenge 32`) and no entry fee or prize JSON. `EventId` (a draft league's `LeagueID`) is the id after the date in mtgo.com league decklist page names (`modern-league-{date}10397`). The `{format} League {date}` names are v1's own.
- A league entry's length is not one number per kind. MTGO's Competitive Sealed League is up to five matches and Friendly Sealed Multi-Stage six (two stages of three; mtgo.com/limited-events), draft three, constructed five. 0.x used six for every sealed league, and since re-entries share the league token and sealed has no draft pool to check the deck against, every sealed run took the next entry's first match (reported on 1.1.2). The panel states the length (`FormatDescription=Play Up to 5 Matches`, `3 Matches`; `panel_round_count`), and the fold uses it, else the kind's default (sealed 5). Entering a league logs `Send Class: FlsLeagueUserJoinReqMessage`, with no league in it, then the league panel in the same second: that pair is a new entry and closes the Active run on the panel's token only (other leagues, joined at the same time, carry on). The entry panel is the next panel after the request, in the same second, in every log on hand (the first panel within five seconds claims it). A join request with no panel by then closes nothing. Pinned by the leagues tests `entering_a_league_again_closes_its_run_whatever_its_length`, `entering_another_league_leaves_this_run_alone`, `a_join_request_without_its_panel_closes_nothing`, `a_league_stating_six_matches_runs_six` and the store's `a_league_entry_runs_its_stated_matches_and_the_next_entry_starts_a_new_run`. The league sync stores the stated length in `leagues.rounds` (migration 0025; NULL takes the kind's default), and the Limited pages, the dashboard bars and the league overlay card count rounds from it, so a six-match run shows six and 5-1 of six is not a trophy (`a_run_of_a_six_match_league_is_summarized_against_six`).
- Set code is never a field. Derive it from `PlayFormatCd=DHOBHOBHOB` (match block), `PlayFormatCd=HOBx3` (league panel), or the picked cards.
- Not every draft is one set. Vintage Cube is `PlayFormatCd=DC03C03C03` with `GameStructureCd= Vintage Cube x3` (leagues and elimination drafts alike), QuickCube `DINSCUBE` / `QuickCube`, and there are `DSUPREME` and mixed blocks such as `DINPSAP` / `IN PS AP` and `DUZULUD` / `UZ UL UD` (seen in the API's `match_log_samples`). A cube's picks span every era, so "the most common set among the picks" names a random one (`PRM`, `EXO`, `MH3`). A code that is not one set repeated is the whole body after `D` (`INSCUBE`), a code from a format code always replaces a guess from the picks (the draft usually links before any match, so the guess comes first), and the pages name such a run by its `GameStructureCd` (`Vintage Cube`), not its code (issue #492).
- Only `FlsBoosterDraftPickSucceededMessage` with `"IsReservation":false` is a committed pick; reservation acknowledgements are noise.
- A pick's `shown_at` is the PendingPick line's local `HH:MM:SS` placed on the local date of the pick's `EndTime` deadline, stepped back a day only when that lands more than 12 hours after the deadline (0.x `ConvertMtgoTimestamp`). It never steps forward, so if the local clock runs ahead of MTGO's server near midnight (a line written just after local midnight whose deadline falls just before it), `shown_at` lands about 24 hours early. The draft then looks quiet to the 30-minute routing rule and that pick's token-less selection lines are dropped; the commit ack still records the card.
- A league match without `PlayFormatCd` cannot be placed by format. Since Plan R the league sync folds every league input once (`fold_league_runs`, constructed and limited together) and the pages read the stored `leagues` rows, so a format-less match followed by a limited match on the same league token is one draft or sealed run holding both, on every page. (Before, the Leagues page and the Limited pages folded separately and the first match was also a constructed run on its own.) Real join blocks always carry the code; the case is pinned by `the_format_less_then_limited_case_is_one_limited_run` (store) and a `leagues` test.
- A late adoption retires a run key. When the course-less run holding a draft league's matches adopts the draft (0.x `AdoptCourselessDraftLeague`), the draft's own run (`draft:{token}`, or `0x:{id}` for a 0.x one) goes. The adopting run lists that key in `former_keys`, so notes and drops saved under it still reach it. The reverse case is not tracked: draft lines from an older log that arrive later can turn a run keyed `{league token}:{first match}` into `draft:{token}`, leaving its notes under the old key.

## Game state frames and game log files

- **Game state frames** (`Game Play Status Update for Game ID: N, Match ID: M`) are full snapshots of `Players` (Id, Name, LibraryCount, HandCount, Life) and `Cards` (Id, CatalogID, Zone, ActualZone, Owner, Controller). They carry no clock. Only the local player's Hand, Library and Sideboard are visible; the opponent shows public zones only. About 60% of frames repeat the previous one byte for byte, so skip repeats before doing work.
- **The first frames of a game can be placeholders**: an opponent with `HandCount 0` and `LibraryCount 0` before the deal. Opponent mulligans must start from the first frame where the library is non-empty.
- **A `Stack` entry is a spell or an ability, and frames do not say which.** An ability carries its source's catalog id, so an ETB trigger or an activated ability looks like a second copy of the card. Skipping every stack entry (0.x) shows a spell being cast as still in the library. The draw odds read the card instead: an instant or sorcery is a spell, a land is an ability, and any other card is an ability only while a copy of it is on the battlefield (`overlay::draw_odds`).
- **The dealt hand is in the frames before the play or draw choice.** The local Hand zone fills while the die roll winner is still choosing, so anything live that reads the hand (the overlay's draw odds) waits for "chooses to play" (or a kept hand, or a card in a public zone) before using it (`overlay::before_play_draw`).
- **`Zone` and `ActualZone` can differ** (a card played from exile, a companion). 0.x reads `Zone`.
- **A multi-face card logs its face under the face's own catalog id (#320).** The face's `cards` row is a stub named by the log, with no oracle id. Card stats resolve it by that name to the card with a face of that name (0.x `resolveFaceNamesToOracle`), only for the local side's non-deck rows and the opponent's rows, as 0.x did. v1 splits every card name on ` // `, so it also finds a middle face of a three-face name, which 0.x's SQL prefilter could not; no real three-face MTGO card is known.
- **An oddly typed frame field is coerced, not fatal (#155).** No real log is known to have one: this is defensive parity with 0.x, which read frames through PHP casts. A number field is read as `(int)` (a fraction cut, a string's leading number, `true` as 1), a text field as `(string)`, a `CatalogID` that is no valid `u32` is 0, a list that is not a list is empty, and a list entry that is not an object is skipped (0.x would have thrown there). Known gaps with PHP, none possible in a real frame: leading whitespace is trimmed as Unicode (PHP trims ASCII only), an out-of-range number saturates (PHP wraps), and `(string)` of a huge float gives digits rather than PHP's `1.0E+20`. Add a fixture if a real shape ever turns up.
- **On the draw, the first draw lands in the kept hand before the first local play**, so the hand read from the frames can show 8 cards. The game sync stores that last card as `first_draw` (outside the opening hand), and the match page shows it last with the "T1 draw" pill.
- **After bottoming, the starting hand line names more than the player**: "NAME puts a card on the bottom of their library and begins the game with six cards in hand." A name pattern that allows spaces (0.x's) captures "NAME puts a card on the bottom of their library and" as the player. The game detail reads the line with `mtgo_protocol::entries::BEGINS`, the lazy pattern above, so the hand belongs to NAME.
- **`deck_used` is often logged twice for one game.** Use only the first per game, by log position, or quantities double.
- **`Match_GameLog_<token>.dat` timestamps are local wall-clock .NET ticks**, not UTC. Convert with the machine's timezone. A truncated last record (the file is still being written) must be dropped, not read.
- **The MetaMessage text fallback is a subset of the `.dat` log**: only whitelisted phrases decode, so a game log built from it misses lines such as "draws a card".
- **Log lines pair with frames by `HH:MM:SS` only.** A frame's time is its header's time of day (no date, no milliseconds for log frames) and a game log entry's is `H:i:s` local, so the viewer pairs a log line with the first frame in or after its second by the first eight characters. Several frames share a second, and a game crossing midnight wraps back to `00:00:00`. Frames dropped as repeats (replays spec ruling 4) move a pairing to the next changed frame.
- **A log match whose game sync errors is never stamped or detected (#300 F11).** Archetype detection and card stat reporting wait for the game sync's rows. If the sync fails for a match (a corrupt game log, a store error), the match gets no `archetypes_detected_at` marker and no detection, and it is not reported. It stays out of the queue until a later game sync of that match succeeds (a rebuild, or a card data change that re-syncs it).

## Game history files

- **`mtgo_game_history` is a .NET BinaryFormatter stream**, and MTGO keeps several copies (one per ClickOnce install folder). Merge them by match `Id`, the last file winning.
- **The list's `_items` is its capacity, not its count.** A 671-match history has 1024 slots: 671 references, then one null run for the rest. Read only `_size` items. Count array elements, not records: a null run is many elements, and a reader that counts records swallows the records after the array (0.x does, and gets away with it because objects register by id).
- **A paired game log can name only the opponent (#180).** The local player is then unknown, never the only name in the log: 0.x took the first player and stored the opponent as the local account. v1 leaves the local player empty, so the import uses the fallback account and reads no games from that log.
- **`StartTime` is local wall-clock time** with the `DateTime` kind in the top two bits. Mask them off before reading ticks.
- **`GameWins` and `GameLosses` are not the result.** A match left at a level score has counts of 1-1 but a winner in `MatchWinners`. Read the result from `MatchWinners` and `MatchLosers` (`mtgo_history::local_verdict`), and the counts only when neither names the player.
- **Player names are not only in `Opponents`.** `MatchWinners` and `MatchLosers` name the local player too, and `Description` is a room title another player may have typed. Anonymise all of them before a file enters `fixtures/`.

## Tournament lines

- **A tournament message's JSON can fail to parse.** `draft_hobbit.log` holds a `FlsTournamentRoundInfoMessage` (about 37 KB) whose outer object does not parse. 0.x's rule (`ExtractJson`, v1 `decks::first_json`: the first balanced `{` or `[` that parses) then returns the inner `Round` object, so that observation's payload has no `Token`. v1 ships it as 0.x did; the API keys observations by content hash and the tournament token travels beside the payload.
- **Tournament events carry no match token**, and the API refuses an observation with neither a tournament nor a match token (the whole batch, every retry). v1 sends `match_token: null` and queues an event without a tournament token as `skipped`.
- **The newest round info naming a match may not carry a readable tournament token.** A damaged or truncated `FlsTournamentRoundInfoMessage` still contains the match token, so a text search finds it first. 0.x stops at that newest hit and leaves the match unlinked; v1 passes over a line whose token does not read and takes the newest one that does.
- **Round info JSON misses exactly one closing brace.** Every `FlsTournamentRoundInfoMessage` in `fixtures/tournaments/challenge_showcase.log` (and `FlsTournamentStartDeckBuildingMessage`) fails to parse until one `}` is added; the repair rule of the draft payloads (`first_object`: up to three closers from the text's own bracket balance) fixes all of them. Lines reach 230 KB for 150 matches.
- **The round info reader adds back one closer, not three.** The draft repair adds up to three, but a round info line cut short inside (a log cut mid-line) would then decode as a partial round with fewer matches. The tournament decoder allows exactly the one the fixture misses (`ROUND_INFO_MISSING_CLOSERS`), so a line missing more than that decodes to nothing instead of a wrong round.
- **A match can stay in progress after its round is over.** A match left `in_progress` from an earlier round (no close line ever logged) must not make the tournament live. The event card counts a tournament match as live only in the standing's current round, or when the round is unknown (`live_in_round`).
- **Middle rounds known only from a restart snapshot have no playoff flag.** A round paired live carries `InPlayoffs`; a round that arrives only in a snapshot does not, so it never moves the Swiss round count. The corrections (a round paired live in the playoffs ends the Swiss just before it) read live rounds only (`Folder::swiss_rounds`).
- **A marker in a stack trace is not the message.** `(UI|CreateAndFlipToDuelScene)` and `(UI|Flip To Game Side: DuelSceneViewModel)` entries carry a .NET stack whose frames name `FlsTournamentRoundInfoMessage`. Every real message has its marker on the entry's header line (`Processing Registered Handler for X in State`), so v1 reads markers only there.
- **"Joined" in a match state does not mean the account joined.** Other players' matches log `MatchNotJoined...` and `MatchJoinedCompletedState`. The account's tournaments are those with a `Tournament State Changed ... to` a state containing `Joined` but not `NotJoined` (`PremierJoined*`, `TournamentJoined*`); a later change to a `NotJoined` state is an unregister.
- **Everything repeats.** Round 1 info is logged twice in the same second (identical), the joined event's `EventSyncData_t` three times at login, every tournament chat line twice, and states change to themselves (`PremierJoinedAwaitingMaxPlayersState -> PremierJoinedAwaitingMaxPlayersState`). Fold per round number, first seen wins.
- **Snapshots come only at login.** `EventSyncData_t` for a joined event arrives at login and registration, never during the event. After an MTGO restart mid-event it carries the full `Rounds[]` with `Results[]`, so a restart can rebuild.
- **The template match time lies.** `TournamentSyncData.MatchCreateInfo.MatchTimeInMinutes` says 25; the round's own matches (`Round.Matches[].MatchSyncData.MatchCreateInfo.MatchTimeInMinutes`) say 50, as does `RoundLengthInMinutes`.
- **The prize text is cut at 255 characters**, mid-table (`Rounds: 129-212 8; 213-384 9; 3`). Only whole `A-B N` pairs can be read.
- **Swiss rounds is not `ceil(log2(players))` everywhere.** `NumberOfRounds` is 0 for every Challenge (Preliminaries say 4). The formula matched all 5 Challenges in the fixture (27 to 46 players), but MTGO's own table gives 9 rounds for 213 players, where the formula gives 8. v1 uses `NumberOfRounds`, then the prize text's whole ranges, then the formula only up to 128 players, else unknown.
- **The cut is invisible in the tournament states.** The tournament stays `...RoundInProgressState` / `...BetweenRoundsState` through the playoffs. Only `FlsPlayerEventStateChangedMessage` says `InPlayoffs: true` (with `NewState` 24 between rounds, 23 when a round starts). The missed-cut eliminations (`EliminationReason: 1`, one per player) come in the same second as the last Swiss round's result, before `InPlayoffs: true`.
- **A round's matches are `Round.Matches[].EventToken`** (the match token); `MatchCreateInfo` sits under `MatchSyncData`, not at the top of the match.
- **Results keep everyone.** `FlsTournamentRoundResultMessage.Results[]` lists every registrant, eliminated and dropped ones included, with a unique `Rank` (tiebreaks), and `OpponentResults[]` holds games (`Win`, `Loss`, `Draw`) per round and `Bye: 1` for a bye. `Points = 3 x match wins + draws` on every row seen. The win percentages are strings (`"0.33333"`).
- **The account's match ending does not end the round.** The tournament stays `TournamentJoinedRoundInProgressState` until every match of the round is over (32 minutes after the account's round 1 win). MTGO logs a state change for every match of a joined event's round, ending in `TournamentMatchClosedState` (others) or `TournamentMatchJoinedCompletedState` (the account), so the open matches can be counted; the last close comes about a second before the round result.
- **Compaction hides the account's own match.** 10 minutes after the account's match ends, its log events move to `match_event_archives`, while the round can run for another 30 minutes. Read the account's match from its `matches` row, not from `log_events`.
- **Registration and between-round chat are not stored.** `FlsPlayerEventNewPlayerOrderMessage` repeats the whole player list (with names) on every registration, about 1.6 MB per event; the chat says "approximately 2 minutes" every time (measured 2 min 09 s), so v1 uses a 2-minute constant after the round result. `PlayerRevisionNumber` in the snapshot and `RevisionNumber` in the list share one counter.
- **`EliminationReason` meanings are inferred.** `2` looked like a drop (0-point players leaving), `1` like removal by the event (missed cut, playoff loss, and 4 round 1 players within 5 seconds, likely no-shows).
- **Times inside tournament JSON carry an offset** (`2026-11-22T17:00:09.6680000+01:00`, seven fraction digits); `SideboardingEnds` is the placeholder `1970-01-01T01:00:00+01:00`. Log line times have no date.

## Imported games: the postboard rule

- **A sideboard card can show in the log as another printing (#296 S7-2).** A sideboard card registered under one catalog id can show in the log as another printing (warp variants have their own catalog id). v1 matches it by oracle id when card data knows both and that printing is not itself in the registered list. The registered row then gets the deck columns and the copies seen, and the variant's counters stay on its own row (card stats group printings by oracle). Without card data, or with another oracle id, the log card is not matched.

## MTGO on macOS

- **MTGO on a Mac runs under a Wine wrapper or in a Windows VM, and every wrapper keeps its prefix somewhere else.** v1 searches `~/.wine`, CrossOver bottles (`~/Library/Application Support/CrossOver/Bottles/*`), Whisky bottles (`~/Library/Containers/com.isaacmarovitz.Whisky/Bottles/*`), MTGO-OSX prefixes (`~/Library/Application Support/MTGO-OSX/Prefixes/<arch>`) and the prefixes inside Sikarugir and Kegworks wrapper apps (`~/Applications/<wrapper>/*.app/Contents/SharedSupport/prefix`). MTGO-OSX is confirmed on the owner's Mac (2026-11-17): the log is `Logs/mtgo.log` in the `mtgo..tion_*` folder beside `mtgo.exe`, and it appears only after the first login. The others are each wrapper's default layout, not yet confirmed by a tester log; record any wrapper whose log turns up elsewhere here.
- **CrossOver names the Windows user `crossover`**, not the macOS user, so the Mac search tries both.
- **A VM's log lives on the VM's disk.** Nothing on the Mac can find it; the user shares MTGO's folder from the VM and chooses it in Settings, File paths. Tailing polls, so a shared folder that sends no file events still works.

## Arena

MTG Arena's `Player.log` (spec `2026-11-03-arena-support-design.md`, sections 3 and 4). Parsing lives in `crates/arena-protocol`; tests named below are in its `split`, `decode` and `clock` modules unless a crate is named.

1. **Seat is not fixed.** The local player is seat 1 in one match and seat 2 in the next. Find the local seat by user id (`authenticateResponse.clientId` against `reservedPlayers[].userId`), never by seat number. Pinned by `decode_reads_room_state_seats` and `decode_reads_seat_two_in_match_two`.
2. **Results are cumulative.** Every game over message carries the whole ordered result list so far, and the final one ends with a `MatchScope_Match` entry. One line can even hold two game states, the second adding the match entry. Filter to `MatchScope_Game` first; then entry n is game n. Pinned by `decode_reads_cumulative_results` and `decode_reads_game_over_results_from_diffs`.
3. **A match can end after one game.** Conceding the match (`concedeReq.scope: MatchScope_Match`) ends a Bo3 at 0-1, with no `SubmitDeckResp` for the next game. Never derive the match result from game counts: read the `MatchScope_Match` entry. Pinned by `decode_reads_match_concede_scope`.
4. **Default fields are omitted.** A rank response for Bronze tier 4 with no steps is `{"constructedSeasonOrdinal":95,"constructedLevel":4,...}`; `constructedMatchesLost` is absent when 0. Missing means the protobuf default: `Bronze` for the class, 0 for numbers. The ladder list `constructedRankInfo` confirms it: its Bronze entries are the only ones with no `rankClass` (owner logs, 2026-11). That list also starts below Bronze with `Spark`, levels 4 to 1 of five steps each (Bronze to Diamond tiers have six); limited has no Spark. `rank_steps` puts Spark below Bronze 4 step 0, as -20 to -1, so every other step value is unchanged. Pinned by `decode_fills_rank_defaults` and `spark_sits_below_bronze_in_tiers_of_five_steps` (`crates/arena-match`).
5. **Stale responses.** At one login a season 89 rank answer came 15 s before the season 95 one. The decoder reports both; the projector drops any rank observation whose season is not the current season. Pinned by `decode_keeps_stale_rank_responses` (the drop by the projector's `stale_season_rank_is_dropped`).
6. **Rank responses carry no user id.** Attribute them to the account from the latest login line. `ArenaEvent::Rank` has no account field for that reason; the attribution is pinned by the projector's `rank_before_any_login_is_held_until_the_login`.
7. **Card names are not in the game state.** `gameObjects[].name` is a localisation id; the card is `grpId`. grpIds (for example 71291) fall inside the MTGO catalog id range, so an unmapped grpId must never be treated as a catalog id. The decoder keeps grpIds as `grp_id` and plain `u32` lists, never catalog ids; the id offset is the card identity task's.
8. **Instance ids change** when a card changes zone (`AnnotationType_ObjectIdChanged`, 119 in the sample). The first release reads no game objects, so nothing pins this yet; match detail must.
9. **Game state comes as diffs** (4 `Full`, 778 `Diff` with `prevGameStateId`). The decoder reads only `gameInfo` and turn 1 `turnInfo`, which come in diffs too, so it never needs a full state. A turn 1 `turnInfo` repeats in every diff of turn 1, and only the message that also has `gameInfo` names its game. Pinned by `decode_reads_game_over_results_from_diffs` and `decode_reads_first_turn_with_its_game`.
10. **Mixed JSON layout.** API requests are one line (`==> Name {json}`, the request itself JSON inside a string); responses are a date header line, a `<== Name(id)` line and a JSON line; server to client game messages are a header line then one JSON line, sometimes holding several messages; client to server messages are a header line then pretty printed JSON over many lines, which tailing can catch half written. Pinned by `splitter_pairs_a_response_with_its_json_line`, `splitter_keeps_the_date_header_of_a_response`, `splitter_reads_a_multi_line_client_block`, `splitter_holds_back_an_unfinished_json_block`, `split_complete_equals_pushing_byte_by_byte` and `decode_all_reads_every_message_of_a_line`.
11. **Header times follow the machine locale and zone.** `03/11/2026 12:33:02` is DD/MM on the sample machine, with no zone. The date order comes from a field above 12 or, when every date is ambiguous (the sample's are all 03/11), from the GRE time on the line after a header; the machine offset is passed in. Prefer GRE (unix ms) and client (.NET ticks, UTC) times. Pinned by `header_time_reads_day_first`, `header_time_applies_the_offset`, `detect_day_first_from_the_fixture` and `dotnet_ticks_match_the_gre_time`.
12. **Game messages: the seat, the queue and the noise.** The local seat is `systemSeatIds` on every GRE message (the seat a message is addressed to), not a field of the game state. `GREMessageType_QueuedGameStateMessage` is part of the state sequence like a normal game state and must not be dropped. `GREMessageType_UIMessage`, `GREMessageType_TimerStateMessage` and the client's `ClientMessageType_UIMessage` are noise; `arena_protocol::game_messages` drops them (`fixture_counts`, on `bo3-three-games`).
13. **A match's first game message names no match.** The `GREMessageType_ConnectResp` (game 1's deck) carries no `gameInfo`, and in the second match of `bo3-loss-and-match-concede` it comes before that match's `Playing` room state, right after the previous match's `MatchCompleted` one. Attaching it to "the current match" gives it to the finished match. The tracker ends the current match at its completed room state and holds unnamed messages for the next match named. Pinned by the tracker's `stores_game_messages_of_the_fixture_match` (every match starts at its connect response) and `a_completed_room_state_ends_the_current_match`.
14. **Between-game messages carry no game number.** After a game's `GREMessageType_IntermissionReq`, the sideboarding messages (`GREMessageType_SubmitDeckReq`, the client's `ClientMessageType_SubmitDeckResp`, `SubmitDeckConfirmation`) have no `gameInfo`; the next game's number first appears in its opening game state (`bo3-three-games`: intermission at line 4716, deck submit around 4753 to 4780, first `"gameNumber": 2` at 4910). They belong to the next game, so the tracker moves to the game after the latest `gameInfo` at each intermission. Arena can send the same intermission twice (`bo3-loss-and-match-concede`, after an `IllegalRequest`), so it counts from the game info, not from the previous intermission. Messages after the final intermission take a game that never comes. Pinned by the tracker's `between_game_messages_take_the_next_game` and `an_intermission_moves_later_messages_to_the_next_game`. A restart while sideboarding (after the intermission, before the next `gameInfo`) must resume at the next game too: the stored events only give the latest `gameInfo`, so the Arena source's start moves on only when a stored intermission comes after the match's last stored message with a `gameInfo`, in log order. A stored game number is not enough: the repeated intermission is stored as the next game (game 3 in `bo3-loss-and-match-concede`), before that game's own `gameInfo`, and treating it as the end of game 3 would file the rest of game 3 (its mulligan included) as game 4 after a restart mid-game. Pinned by the tracker's `a_restart_while_sideboarding_keeps_the_next_games_deck`, `a_restart_mid_game_three_keeps_its_game` and `a_restart_anywhere_equals_one_read`. The summary also ignores deck messages after a game's intermission when it picks that game's deck (`deck_messages_after_the_intermission_are_not_the_games_deck`), for matches stored before that fix.
15. **A revealed card is a copy, not the card.** A card the opponent reveals from hand shows as a `GameObjectType_RevealedCard` in their `ZoneType_Revealed` zone, with its own instance id, while the card itself stays hidden in the hand. Counting both would see the card twice. `arena_game::summary` matches a revealed copy to its later public card only when the reveal ends in the same game state as a card of that grpId leaves the opponent's hand (cast or discarded as the reveal ends); a reveal that ends any other way (the card stays in hand, or leaves in a later state) counts as a card of its own, so the opponent's seen count can be one too many for that card.
16. **Large game state messages are summarized, with no JSON.** When a message's game states hold more than 50 game objects or 50 annotations, Arena writes `[Message summarized because one or more GameStateMessages exceeded the 50 GameObject or 50 Annotation limit.]` and `::: GameStateMessage` lines with counts instead of the JSON (owner logs: 4 such entries, each a hole of 1 to 5 `gameStateId`s; the summary's count need not equal the number of ids lost). The states are lost to every log reader, and a full state comes about once per game, so a record must not wait for one: the `.mtgr` writer writes the gap as `incomplete` and keeps folding the diffs after it (`crates/arena-game/src/mtgr/gaps.rs`; pinned by `summarized_gap_continues_to_the_real_result`). A zone changed only in the lost states stays stale until Arena sends it again, so the writer also checks each library against its own lines before a keyframe.
17. **Faces and halves show their own grpIds.** A double-faced card shows the face up (`grpId`, `othersideGrpId`); a split card or Room being cast shows the half's grpId, with `GameObjectType_SplitLeft`/`SplitRight` (`RoomLeft`/`RoomRight`) children, and card data has only the card's grpId. Take the card's grpId from the same card shown whole elsewhere in the game, not from numbering (`crates/arena-game/src/mtgr/faces.rs`).
18. **A diff's silence means unchanged, and a missing field means false or zero.** `gameObjects[]`, `zones[]` and `players[]` entries are always sent whole, so an object, zone or player a diff does not resend is unchanged, and a field a resent entry leaves out is false, none or zero. Arena drops `isTapped` when a permanent untaps (161 times in the two fixtures, never `"isTapped": false`) and drops `attackState`, `blockState`, `attackInfo` and `blockInfo` after combat. `turnInfo` is sent whole too (a missing `step`, `priorityPlayer` or `decisionPlayer` means none), but a diff with no `turnInfo` leaves the turn as it was. Persistent annotations (counters, attachments) stay until `diffDeletedPersistentAnnotationIds` names them. The rules are in the `crates/arena-game/src/state.rs` header; pinned by `fold_keeps_object_details` and `fold_keeps_turn_and_priority`.
19. **A zero life total is dropped.** Arena's JSON leaves zero values out, so a player entry at 0 life has no `lifeTotal` (the owner's logs show `PlayerStatus_PendingLoss` entries without it after lethal damage). Reading a missing `lifeTotal` as "unchanged" leaves the loser alive. Pinned by `fold_reads_a_dropped_life_total_as_zero`.
20. **Keeps and the starting player's choice are pending messages, not actions.** The opponent's mulligan decision is never logged as an action. Each player entry carries `pendingMessageType`: while a seat waits on `ClientMessageType_MulliganResp`, it is deciding; a rise in `mulliganCount` is a mulligan, and the pending message clearing without a rise is a keep. Likewise the seat a state waits on for `ClientMessageType_ChooseStartingPlayerResp` is the one choosing who plays first (the die roll winner in game 1, the loser of the previous game later). Arena does not annotate hands either: a card appearing in a hand unannotated in the pregame is the opening hand or a mulligan redraw. Pinned by `fold_keeps_pending_messages`, `keeps_follow_the_pending_mulligan_response` and `starting_chooser_is_the_pending_seat`.
21. **The companion moves through a proxy.** A companion starts in `ZoneType_Sideboard` (zone 34). Putting it into hand is a `UserActionTaken` with action type 7 (the companion special action), a `RevealedCardCreated`, and a zone transfer of the revealed proxy object rather than the card, sometimes without the proxy object being shown at all (Kaheera's proxy 597 in `bo3-loss-and-match-concede`). Pair the move with its card by the proxy's zone, owner and grpId; when not exactly one candidate pairs, write `incomplete` rather than drop the move. Pinned by `companion_is_revealed_then_put_into_hand`.
22. **A partial `Shuffle` is a random order, not a shuffle.** `AnnotationType_Shuffle` with `OldIds`/`NewIds` covers a whole library for a real shuffle (owner matches: 49, 41 and 38 cards), but Arena also uses it to renumber only a few cards it put on an end in a random order (cascade, "the rest on the bottom in a random order"; `bo3-three-games` lines 12186, 23598, 23618, 28539). Writing those as `shuffle` invents a shuffle. The `OldIds` to `NewIds` pairing is no evidence of which card went where, so two or more such cards are `bottom ?` and lose their identity; a single one keeps its place and identity. Arena can also renumber a card it never moved: "put the other on the bottom" is a `Shuffle` of the one card left at the bottom, with no `ZoneTransfer` (`bo1-wins-and-concede` line 10654, `sealed-direct-fast-login` line 11280). Tell a random end from a shuffle by the library as the state shows it (the renumbered cards make up one end, with other cards beside them), not by comparing the count with the library's size before the message: cards put on the bottom of a smaller library outnumber it. Pinned by `partial_library_reorders_are_not_shuffles`, `fixture_partial_shuffles_are_random_bottoms`, `random_bottom_of_a_tiny_library_is_no_shuffle` and `one_card_renumbered_on_the_bottom_keeps_its_place`.
23. **Countered has two shapes.** A countered spell is a `ZoneTransfer` with `category` `Countered`, its affector the resolving counterspell (5 in `bo3-loss-and-match-concede`). A countered ability has no annotation at all: the ability object is deleted while another object resolves (`bo3-three-games` 6:13, a ward trigger countering Barrels' ability). Pinned by `countered_spells_are_written_countered` and `countered_abilities_cease_by_the_counter`.
24. **Looks are reported only in the local player's prompts.** Arena tells nobody what the opponent looked at. The local player's looks at their library show only in the prompts sent to them (`systemSeatIds` is the local seat alone): `GroupReq` with `GroupingContext_Surveil` and `SelectNReq` over library instance ids (`unfilteredIds` lists every card shown, `ids` only the choosable ones). Scry results come as their own `Scry` annotation, and `GroupingContext_LondonMulligan` is a hand, not a look. Pinned by `local_looks_at_library_cards_are_written` and `private_looks_and_searches_give_no_origin`. A search is not reported either: it shows only as a `ZoneTransfer` out of the library and a `Shuffle` of the whole rest of it, and the `Shuffle` comes in a later message, not the one that moves the card: the next one for a fetch land (`bo1-wins-and-concede` gsids 259 and 260, `sealed-direct-fast-login` 69 and 70, 333 and 334, 420 and 421), two and three later when each player searches (gsid 322, then 324 and 325), always before the resolution's `ResolutionComplete`. A searched card that happened to be at an end of the library gets no origin position (#843). Pinned by `searched_cards_shuffled_in_a_later_message_give_no_origin`. Because the opponent's looks are never reported, an opponent card that leaves the library for a public zone tells where it was only when it was revealed there: Arena shows such a reveal by turning the cards `Visibility_Public` in the library (with `GameObjectType_RevealedCard` proxies and `CardRevealed` persistent annotations), and moves them in a later state (Cavalier of Thorns' top five at `bo3-loss-and-match-concede` line 6218, an explore at line 18226). Two cards put into a graveyard from an unreported look are not a reveal of the top two (#599). Pinned by `opponent_cards_from_a_hidden_look_get_no_origin` and `new_library_cards_take_public_positions`.
25. **Some families are reported only in part.** No annotation ever reports a change to a spell's cost (12 matches). Searches are not reported: a tutor shows only as a move out of the library and a shuffle. A lasting effect (`LayeredEffectCreated`) names its source, effect id and affected objects but no rules text, no stated duration and no delayed triggers. The `.mtgr` writer marks these with `Omits "costs"` and `Partial "library effects"`, and writes `?` for an effect's text (mtgreplay/standards issues #1 and #2).
26. **Card data: Universes Beyond printings hide behind Through the Omenpaths.** An Arena grpId is a printing. On MTGO, a Universes Beyond card (Spider-Man, `SPM`) is the Through the Omenpaths printing (`OM1`), and the MyMTGO API maps its MTGO ids to the `OM1` row, so its import skipped the `SPM` printing whose MTGO id was already mapped, and that printing's `arena_id` with it: Multiversal Passage (grpId 97998) came back unknown. Fixed in mymtgo/api#37 (an `SPM` row with its own `arena_id` and no MTGO ids). New Arena sets also have no `arena_id` on Scryfall for days after release (Reality Fracture, `FRA`, 2026-10-02), so the client's 7-day recheck of unknown cards picks the names up once Scryfall has them. Until then the replay still opens, with those cards written as `?` (entry 27, decision 0048).
27. **New sets stay unnamed for weeks, and the log never names a card.** On 2026-11-05 Scryfall still had no `arena_id` for any Reality Fracture (`FRA`, released 2026-10-02) printing, over 400 of them, so grpIds such as 106282 (Darklight Phoenix), 106333 and 106334 (Carnivorous Cultivator // Enroot), 106371 (Ferocity of the Hunt) and 106504 (Garruk, Curse Breaker) have no card data, and neither do 81181 and 81182 (a special Swamp and Mountain printing). The log has only localisation ids for names. The `.mtgr` writer writes such a card `?` with `src arena:<grpId>` (decision 0048) instead of refusing the replay; the replay is built on read, so it gets the name when the card data does. Pinned by `unknown_cards_are_written_with_unknown_names`.
28. **Token names are not Scryfall's names.** Arena gives a token no name and usually no card data, so the writer names it by its subtypes followed by "Token" (CR 111.4: "Treasure Token", "Lander Token", "Map Token"). Scryfall names the same token by its subtypes alone ("Treasure"), and a token row for it, from either platform, holds that name and a `Token ...` type line. Look token art up by the subtypes; never let a token row name a token in the record. Pinned by the store's `arena_replay_tokens_take_token_art_by_name`.
29. **A fast login writes no login line.** When Arena logs in with a remembered token (`WizardsAccountsClient:RefreshToken_LogIn`, `TryFastLogIn`), it never writes `[Accounts - Login] Logged in successfully. Display Name: ...` (`bo1-wins-and-concede` has none in four sessions). Waiting for that line finds no account and drops every match of the session. The account is in the `authenticateResponse` instead: `screenName` is the display name and `clientId` the user id (`bo1-wins-and-concede` line 1450). **The screen name can come without its `#` tag, every time.** A tester's log (`sealed-direct-fast-login`, 2026-11-07) has five fast logins whose `screenName` is the bare name, and the tagged name appears nowhere in the file (the Bo3 fixtures' `screenName` is bare too, after their login line). A bare name could match an MTGO username, and `registry_id` would then put the match on that MTGO account, so such an account is keyed `arena:<user_id>` (MTGO names cannot hold `:`), with the bare name in `accounts.display_name`, or the local seat's `playerName` for events stored before bare names were decoded. A later login line whose name before the tag is that bare name (or any login line, when no bare name is known) names the same account, and the store renames the row by its user id. Every store write under an `arena:<user_id>` name (account, match, deck, rank, course snapshot) lands on the account that holds that user id, whatever a login named it, and an untagged name never replaces a tagged one: an upgraded tester database holds the tagged row from before untagged names, a rename and a snapshot can share one batch, and two accounts can share a machine. When a tagged screen name and a login line both appear they name the same account. **A rename can be named before it is authenticated:** the new name can arrive with no user id (a login line) before the `authenticateResponse` that carries the id the old name's row holds, so the new name first gets a row of its own and its matches, decks and ranks are stored under it. The authentication then merges that row into the one holding the id, which takes the new name (#538, pinned by the store's `a_rename_before_authentication_merges_into_one_account` and `a_rename_before_authentication_ends_the_same_in_one_batch`). Pinned by `authenticated_reads_the_screen_name`, the projector's `a_fast_login_session_finds_the_account`, `a_login_line_and_an_authenticated_agree`, `an_untagged_fast_login_is_known_by_its_user_id` and `a_login_line_names_the_untagged_account`, the store's `an_untagged_arena_account_keeps_its_display_name_until_named`, `an_untagged_login_never_renames_a_tagged_account`, `an_untagged_name_without_a_user_id_joins_the_account_holding_its_id` and `a_snapshot_under_an_untagged_name_joins_the_renamed_account`, the tracker's `unstored_matches_of_a_bare_fast_login_join_the_account_named_later`, and fixture-tools' `bo1_fixture_has_four_bo1_matches` and `sealed_direct_fixture_is_a_limited_run_of_an_untagged_account`.
30. **A match's kind is `matchWinCondition`, not the queue name.** `gameInfo.matchWinCondition` is `MatchWinCondition_SingleElimination` for Bo1 and `MatchWinCondition_Best2of3` for Bo3, and the projector stores `game_structure` `bo1` or `bo3` from it. The event name prefix (`Traditional_`) is only a fallback: Bo1 queues have none (`Explorer_Ladder`, `Explorer_Play`) and Bo3 queues have it. Events stored before this change have no `win_condition`, so for them a decoded `best_of_three: false` is Bo1 only when the event name lacks the `Traditional_` prefix; with the prefix it is an old Bo3 whose win condition was not kept. Pinned by the arena-protocol decode tests, the projector's Bo1 tests and fixture-tools' `bo1_fixture_has_four_bo1_matches`. The win condition says the kind, not whether the match is tracked: Quick and Premier Draft, Sealed, Brawl and direct challenges are `SingleElimination` too (Brawl queues are tracked since the Brawl work, entry 36; direct challenges are not) (Traditional Draft is `Best2of3`). Only the queue name decides that: `parse_event_name` accepts constructed `Ladder` and `Play` queues, and draft and sealed events that name a set (`PremierDraft_FRA_20260929`, `ArenaDirect_EOE_Play_Sealed_20261106`; an Arena Direct is whatever format its name says, this one EOE sealed), which take MTGO's limited format codes (`DFRAFRAFRA`, `S6EOE`) and `match_type` `limited`. The tracker keeps a match's game messages only once a room state names such an event; any other match's messages (direct challenges, cubes) are held and dropped when it ends. Pinned by the arena-protocol `limited_events_take_mtgo_limited_codes`, the tracker's `an_untracked_event_holds_its_messages_until_it_ends`, `an_untracked_event_keeps_no_game_messages` and `a_sealed_direct_is_tracked_for_an_untagged_account`.
31. **Arena fetches the rank when a match is exited.** The client asks `RankGetCombinedRankInfo` as it leaves a match, so a ranked match normally has a rank reading on each side (the first Arena spec assumed login or profile view only). A Bo1 ranked match therefore fills its own gap on the rank line instead of showing as "played elsewhere".
32. **Header times use two clocks.** API response headers (`<== EventGetCoursesV2(...)`, `<== RankGetCombinedRankInfo(...)`) are written in UTC, while `Match to ...` game headers are in the machine's local time: the tester's log (`sealed-direct-fast-login`, UTC-5, US `M/D` dates) has `11/7/2026 3:58:45 PM` on a courses response and `11/7/2026 10:59:01 AM` on the authenticate response beside it. The owner's machines are on UTC, so the fixtures before it never showed this. Reading every header as local puts a rank reading taken from a response header hours off for a player outside UTC (the fixture's first rank reading lands at 20:38 UTC for a 15:38 UTC login). Fixed (#621): `header_time` reads a head holding `<== ` (a response) as UTC and every other header with the machine offset; the `response_headers_are_utc` test in `crates/arena-protocol/src/clock.rs` pins it, and the sealed fixture's rank readings sit 5 h earlier.
33. **A course snapshot is the whole list, and says little.** `EventGetCoursesV2` answers with every course the account currently holds, not what changed. `CurrentWins` and `CurrentLosses` are left out at 0, so a missing count is 0 (the decode test `decode_reads_limited_courses` reads 0-0 on the fresh Direct). `CourseDeck` holds the pool plus the basic lands added in deckbuilding, so the stated pool is `CardPool`, never the deck (pinned by the app's `the_limited_pages_show_the_fixtures_arena_runs`, which types an added basic and checks the pool total stays 78). A course missing from a later snapshot has ended, and an empty snapshot means every earlier course ended (pinned by the leagues fold's `a_course_missing_from_a_later_snapshot_completes_the_run` and the tracker's `rows_take_catalog_ids_and_an_empty_snapshot_is_one_marker_row`). A snapshot logged before the first `authenticateResponse` has no account to belong to, so the tracker holds it until the account is known (`courses_before_the_account_are_held`, `a_restart_keeps_held_course_snapshots`). The account must have logged in from the snapshot's own file: a new `Player.log` is a new launch, maybe of another account, and its courses and rank readings come before its login, so crediting them to the account the previous file logged in gives one account's runs to another (#632). Snapshots and rank readings wait for a login in their own file or a later one (the tracker's `courses_wait_for_a_login_in_their_own_file`, the projector's `rank_in_a_new_file_waits_for_that_files_login`), and stores a snapshot equal to the previous one only once (`a_snapshot_equal_but_for_its_place_is_the_same`, `a_restart_stores_no_repeat_snapshot`). An Arena draft has no pick events in the log, so its run has a pool of 42 cards and no draft review (`the_arena_draft_and_sealed_runs_open_their_own_pages`).
34. **Only the course says which entry a limited match belongs to.** A limited match carries its event name (`ArenaDirect_EOE_Play_Sealed_20261106`), the same for every entry of that event; the entry is the course, and its `CourseId` is in `EventGetCoursesV2` only. Each entry gets a new `CourseId` (the owner's logs show a fresh one for each `Explorer_Play` entry, DeckSelect to Complete), and an open course keeps its id across launches: Arena asks for the courses at every start, before the queue (`sealed-direct-fast-login` lists `1dc93d86...` in all six sessions). A match with no course around it (a log read before course snapshots were stored, as a tester's rc.1 upgrade showed with 73 Arena Direct matches in one run) therefore says nothing about its entry, and grouping such matches by event alone lumps every entry into one run. Game 1's local deck and sideboard is the whole pool in limited, so the fold cuts course-less matches where the pool changes and never puts a match into a course whose stated pool differs. One pool means nine in ten of the shorter list's distinct cards are in the other, basic lands left out (every list has them): one entry's game 1 cards are inside its `CardPool` (1.0 in `sealed-direct-fast-login`), while random same-set sealed pools share at most about 0.6 and a 23-card deck list against another pool about 0.85 (simulated; no log on hand has two pools of one set). Half, the first threshold, called two different simulated sealed pools one (`same_pool_needs_nine_in_ten_of_the_shorter_list`, `basic_lands_never_count_toward_a_pool`; the leagues tests `course_less_matches_of_one_event_split_where_the_pool_changes` and `a_match_from_another_pool_never_joins_the_course`, the store's `course_less_matches_split_by_their_first_games_pool` and `the_match_end_sync_folds_a_limited_matchs_runs_again`, `the_match_end_sync_leaves_a_match_its_course_fits`). A match whose game messages were never kept has no pool and stays with the match before it.
35. **A recording's token is MTGO's, a 0.x history row's is not.** The recorder (`mtgr-record`) writes the match's own `Match.Token` GUID in its `.mtgr` header, and the case varies between sources, so tokens are compared lowercased (`tokens_compare_lowercased`). Matches imported from the 0.x history carry random UUID tokens instead, so a token alone misses them: the link falls back to the MTGO match id (`a_recording_links_by_mtgo_match_id_when_the_token_differs`). A recording can also arrive before its match exists, because the recorder finishes before the tracker reads the end of the log, so the link is worked out on read, never written (`a_recording_links_to_a_match_that_arrives_later`). The match id link applies only when the recording's token belongs to no other listed match, and the newest import wins a shared id. Within a match a game links by its MTGO game id; by number only when one side has no id and the position is not already claimed, and two different ids never link by number (`clashing_game_ids_never_link_by_number`): a recording that joined at game 2 holds only game 2 (`a_recording_that_starts_at_game_two_opens_game_two`). All in `crates/store/src/recorded_replays.rs`.
36. **Brawl: the queue name is not the card pool, and Competitive Brawl is ranked on the Constructed ladder.** Spec `2026-11-12-arena-brawl-design.md`, section 3 (owner logs, fixtures `fixtures/arena/brawl/brawl_queue` and `brawl_ladder`). `Brawl_Ladder` is Competitive Brawl and is Historic Brawl (its deck's `Format` is `HistoricBrawl`) despite the name; `Play_Brawl_Historic` is the plain Brawl queue, also Historic Brawl. The Standard Brawl queue's event name is still unseen, and precon decks carry `Format` `Brawl`. So the match's format comes from the submitted deck's `Format` attribute (`EventSetDeckV3` `Summary.Attributes`; the course deck is not read for it), and the event name decides only when no deck was seen (a `Historic` part or `Brawl_Ladder` is Historic Brawl). There is no Brawl rank: `RankGetCombinedRankInfo` has no Brawl ladder, and a lost `Brawl_Ladder` match moved the Constructed reading (5 won, 16 lost to 5 won, 17 lost) while a lost `Play_Brawl_Historic` match left it unchanged, so only the `Ladder` queue is `ranked` and it reads the Constructed rank. The orange shield before a commander's name in the Play tab is a format badge, not a rank. Pinned by the arena-protocol `brawl_queues_are_commander_events` and `deck_format_gives_the_commander_format_code`, and the projector's Brawl tests.
37. **The command zone holds both commanders from the first game state, and later the dungeons and emblems.** `ZoneType_Command` carries both seats' commanders as public card objects (with `ownerSeatId`) in the first state that has the zone, so the opponent's commander is known before turn 1. Later objects in the zone (a dungeon, an emblem) are not commanders, so `arena_game::summary` reads the zone once, in the first state that has it, and never again. The deck JSON carries the player's commander as `CommandZone: [{cardId, quantity}]` in `EventSetDeckV3` (`Deck.CommandZone` beside `MainDeck`, empty `Sideboard`) and in the course's `CourseDeck`; a partner deck has two entries. GRE deck messages carry `commanderCards`, so a `.mtgr` deck section gets the commander from there (the spec first said they had none). `gameInfo` has `variant: GameVariant_Brawl`, `freeMulliganCount: 1` and `deckConstraintInfo` (`minCommanderSize` 1, `maxCommanderSize` 2); starting life is 25. A commander is stored as a sideboard row of the deck version (MTGO's `.dek` convention), so in a commander format the sideboard rows are the commanders. Pinned by the arena-protocol `decode_reads_the_commander_and_format_of_a_brawl_deck`, the store's `sync_writes_match_commanders_from_game_one`, `a_match_outside_a_commander_format_gets_no_commanders` and `player_commanders_fall_back_to_the_deck`, and arena-game's `a_brawl_record_lists_the_commander_as_side`.
38. **A match's rank can be last season's.** A ranked match takes the newest constructed reading before it in the log (`match_rank_readings`, migration 0013), whatever its season. Arena reads the rank at login and when a match is exited (entry 31), so a new season normally has a reading before its first match. When it has none (the client stayed open across the season change and the first ranked match of the new season came before any reading of it), that match stores the previous season's last rank and band. Rare, so the rule is left as it is; a reading of the new season after the match does not move it (#618).
39. **A combat tax is paid toward a seat, and only an attack tax names its source.** Mana paid for an attack or block tax (CR 508.1h, 509.1d) is a `ManaPaid` whose affected id is a seat, not an object, so it names nothing it paid for. An attack tax's permanent keeps a persistent `Qualification` with `QualificationType` 59 on the player it protects (Archangel of Tithes while untapped: `bo3-three-games` line 13682, ability grpId 102181), so the `.mtgr` writer pays it `by cost:` that permanent. A block tax has no such annotation (the same Archangel attacking, line 20748; `bo1-wins-and-concede` line 33970), so its payment stays `pay ... by ?`. The attribution assumes type 59 is the only seat-tax `Qualification` there is: it is the only one seen, from one card. Another tax card whose `Qualification` has a different type, in play beside one type-59 source, would have its payments credited to that source; a second type-59 source makes the payment `by ?`. Pinned by `attack_tax_is_paid_by_the_cost_of_its_permanent`.

## Endstep

Endstep (endstep.cc) runs the Forge rules engine on its servers and talks JSON over websockets and REST. MyMTGO reads it through a browser extension and a native messaging helper (spec `2026-11-10-endstep-support-design.md`, sections 3 to 6). The traps come from the owner's captures: Bo1 against the AI first, then a ranked Modern Bo3 against a human.

1. **No wall-clock time on game events.** The extension stamps each frame with its arrival time. Order is the frame order inside the unit, never a time.
2. **Mulligan zone moves are anonymous.** `"a card: Hand -> Library"` has no card id. The full states before and after show the hand.
3. **Seat is an index.** Events carry `"0"` or `"1"` as strings, and the user's seat comes from `myPlayerIndex`. Never assume the user is seat 0.
4. **Card `id` is per game**, not a card identity. The identity is the name (plus printing).
5. **Sockets reconnect.** `REFRESH` and a 240 s reconnect grace mean one match can span several game sockets.
6. **Only Bo1 against the AI was seen at first.** A ranked Modern Bo3 against a human is now captured (`fixtures/endstep/ranked-modern-bo3/`). Drafts and tournaments still need real captures before their parsers are final.
7. **Forge `gameId` is the same for every game of a Bo3.** All three games of the captured match carry one `payload.gameId`. A game is `gameId` plus `matchScore.gameNumber`, never `gameId` alone.
8. **Endstep moves a live match between gateways.** The lobby socket gets `ACTION_REFUSED` with code `NOT_HERE` (the owner gateway, for example `gw-4`, and a retryable flag), then the game socket sends `REFRESH` and `REFRESHED`. The game socket reconnects, so one match is split across two match units. Nothing is lost: the fold reads every unit of the match.
9. **`GET /api/matches/<id>` arrives before the game socket opens.** It lands in the session unit, so the match units classify unknown and are kept. The capture-time bot filter rarely fires; plan 2's import decides bots.
10. **A REST body can be a JSON array**, not only an object (for example `/api/ranked/queues`).
11. **Ranked results come from `GET /api/ranked/results/<id>`**: `status`, `formatId` and `you` with `ratingBefore`, `ratingAfter`, `scoreBefore`, `scoreAfter`, `delta`, `rdBefore` and `rdAfter` (rating deviation) and `rank`. The match body itself has `format`, `formatId`, `ranked`, `gamesPerMatch`, `myPlayerIndex`, `myDeck` and `mySideboard`.

12. **Forge `endReason` values seen:** only `"concede"` so far (all three games of the ranked Bo3 fixture). The fold maps it to a concession and any other value to an unknown end reason; do not assume every game ends in a concession.
13. **Envelope `seq` is per match and runs across units.** A unit's first `seq` is not 1 when the match was split. Order is still unit order then line order.
14. **A match body can be missing.** The match REST body may never be captured (the tab missed it). There is no fallback: the fold returns `Dropped(NoMatchBody)` and writes nothing, and a later unit that brings the body folds the match whole.
15. **Blind pairing hides the opponent's lobby id.** The lobby shows `hidden-<id>` for the opponent while the match body has the real user id. The fold takes the real one from the match body when it has it.
16. **`/api/auth/me` can answer `Unauthorized` before login.** That body is not an account. The fold never reads `/api/auth/me`: the account is the match body's participant at `myPlayerIndex` (a body without a usable `myPlayerIndex` is a spectator and is dropped).
17. **A unit names its match by refs, of six kinds.** `game:` (Forge game id), `match:` (the Endstep match id, the match body's `id`), `db:` (the Endstep db id, which the match body and the ranked result both carry), `lobby:` (lobby match id), `deck:` (a lobby seat's deck) and `deckbody:` (a deck REST body). They are separate kinds because a split match has no one id in every unit, and a deck body must not pull in the units of every match that deck was played in: a deck body is reached by its own `deckbody:` ref, a lobby seat deck by `deck:`. Without the split, a deck captured later rewrote past matches.
18. **A capture can miss a whole game** (issue #674: a tab lost its extension link mid-match). A Bo3 can then fold games 1 and 3 only. The fold numbers games 1 to n and fills a missing number with an Unknown placeholder game (result and end reason Unknown, no times), because the shared write path relies on that numbering. It stops at `MAX_GAMES` (7), since a hostile `gameNumber` must not grow a match without bound.
19. **The deck shown on a match is the deck body at or before the match body**, else the first one after. A later edit of the deck must not rewrite a match already played.
20. **`lobby_ws` repeats `GAME_STATE` and `GAME_EVENT`** with its own small `seq`. The fold ignores them: the game socket is the source.
21. **`GAME_OVER` arrives on `lobby_ws`**, not only on the game socket.
22. **The opponent's hand is `"Hidden card"`.** A full state lists the opponent's hand cards with the name `"Hidden card"`, `faceDown: true` and ids such as `1010000020`. The decoder drops them. Only the viewer's cards carry a printing (`selectedSetCode`, `selectedCollectorNumber`); the opponent's cards and some of the viewer's have none, so the printing is empty.
23. **A stack entry's `sourceCard` can be a card in another zone.** A trigger or ability on the stack (`isAbility: true`) names its source card, which is still listed in its own zone: Hedge Maze's enter trigger has Hedge Maze on the battlefield, a cycled Oliphaunt's trigger has Oliphaunt in the graveyard. The same card id then shows twice in one state. The decoder skips stack entries with `isAbility: true` and keeps only spells as zone `Stack`; counts of cards seen still use distinct card ids, never one per zone entry.
24. **Forge effect objects look like cards.** A full state can list an object such as `"Devourer of Destiny's Effect"` in a player's `commandZone`, with a card id, `isToken: false` and `types: []`. Real cards always carry types (`["Land"]`, `["Artifact"]` and so on). The decoder notes whether a card has types (`StateCard.has_types`), and the fold makes no card row from a card without types in any zone, so an effect never reaches the card lookup.
25. **Event text holds usernames.** A `GAME_EVENT` text line (a draw, a cast, a concession) can name the player by account name. The game log keeps that text as the game's own words, stored and shown locally only; nothing outbound carries it, and fixtures use fake names.
26. **`CARD_REVEALED` can list a whole library.** A reveal effect (a search, a look at a library) can name every card of a library in one event: the cascade at 02:368 lists 21 cards. Its `cardIds` and `cardNames` are parallel lists; a length mismatch or an undecodable entry empties both. Plan 4 reads reveals: each listed card counts as seen once (seen is distinct card ids, never one per event), and a card a state already showed is not counted again.
27. **`CARD_REVEALED.playerIndex` is the viewer, never the owner.** All nine reveals in the fixture carry `playerIndex` `"0"`, the user, whoever owns the cards. The owner is the seat a full state gave that card id; failing that, `ownerEcho: true` marks the user's own card, and anything else is the opponent's.
28. **Reveal `sequenceNumber`s are huge random values, and the envelope `seq` skips beside them.** Other events carry small counts (147, 395); a `CARD_REVEALED` carries values such as 3688963525634690000, larger than a JSON number holds exactly, and one `VALUE_CHOSEN` carries -9007199254740272. The envelope `seq` jumps by 2 or 3 next to every reveal: the frames in between never reach the user. Neither number orders anything; frame order does (trap 1).
29. **Game 1's start is not on the game socket.** The game socket attaches after the deal: its first full state (02:5) already holds both hands of seven, and game 1's `GAME_STARTED` arrives only on `lobby_ws` (01:93). The mulligans and keeps that follow are on the game socket. The replay's pregame therefore draws the first state's hand from a library of Forge's size plus those seven cards.
30. **Card ids restart per game, and hidden ids are reissued.** One id names different cards in different games (95 is Force of Negation in game 1 and Thundering Falls in game 3). A card drawn again after a mulligan keeps its id (game 3: Ugin, Eye of the Storms is 44 in both hands). The opponent's `"Hidden card"` ids (`1010000000` onwards) count up across the match and are new after every redraw and after the bottom (02:5, 02:24, 02:42), so a hidden id never follows a card. The replay gives every object its own id and keeps Forge's only as a key.
31. **The user's sideboarding and concessions go out on `lobby_ws`.** `SIDEBOARD_SUBMIT` (`orderedCards`: the option ids of the main deck, and `promptVersion`) and `CONCEDE` go out only on the lobby socket. The play actions (`MULLIGAN`, `KEEP_HAND`, `CHOOSE_CARDS`, `PLAY_CARD`, `PASS_PRIORITY`, `CANCEL` and so on) go out on the game socket, and a few settings actions (`AUTO_PAY`, `SET_AUTO_YIELDS`, `SET_PHASE_STOPS`) on both. The decoder reads an outgoing `GAME_ACTION` on either socket, and only for `SIDEBOARD_SUBMIT`, `CHOOSE_CARDS`, `MULLIGAN`, `KEEP_HAND` and `CONCEDE`.
32. **The sideboard prompt shows the last game's deck, not the registered one.** Game N's first state has `sideboarding: true` and a `CHOOSE_CARDS` prompt with `contextType: "sideboard"`: 75 `cardOptions`, the first `sideboardState.mainCount` of them the current main deck. The game 3 prompt already shows the game 2 deck. So a game's deck is the user's `SIDEBOARD_SUBMIT` for its prompt (same `promptVersion` and match id, at least 40 cards), read against the options of the prompt it answered, which is kept even when Forge sends the prompt again with a new version (trap 50); with no submit captured, the next game's prompt; else the previous game's deck. Game 1 is the match deck: the captured deck REST body (trap 19), else the match body's card names. `sided_in` and `sided_out` compare each game's main with game 1's, by card name.
33. **The opponent's sideboarding is never sent.** Only the user's deck changes are known, so opponent rows never have `sided_in` or `sided_out`.
34. **`CHOOSE_CARDS` is not always a bottom.** `contextType` says what it is: `"mulligan"` (the cards to bottom), `"sideboard"` (trap 32) or `"opening_hand"` (the `GAME_DELTA` at 04:290; 04:291 is the user's answer). Bottomed cards are not read from the prompt or its answer: they are the opening hand's ids that the first full state after `HAND_SETTLED` lists in no zone, and only when their number equals that event's `mulligans`.
35. **Mulligan events come in pairs and settle once.** `MULLIGAN` without `amount` is the choice (`"Opponent chose to mulligan."`); with `amount` the redraw is done, and a full state follows it. `HAND_KEPT` comes before the bottom, `HAND_SETTLED` (`amount`, `mulligans`) after it, once per seat per game. The opening hand is the hand of the last turn 0 state before `HAND_KEPT`, and each `MULLIGAN` choice sends back the hand held then. A choice or a keep that follows a state of a later turn belongs to the next game (its sideboarding state was lost), so it neither sends back nor keeps the finished game's hand. A capture that joined a game late can put that game's `HAND_SETTLED` on the previous game's record, so only the first one per seat counts. The opponent's hand sizes come from `HAND_SETTLED` alone, since Forge hides its cards.
36. **The match body and `matchScore` number the seats differently.** The match REST body counts wins as `player1Wins` and `player2Wins` (seats from 1); a state's `matchScore` has `player0Wins`, `player1Wins` and `winsBySeat` (seats from 0). So `player1Wins` is the user's seat 0 in one and seat 1 in the other. The fold reads `winsBySeat`.
37. **`turnNumber` is a string in states and a number in events.** `"turnNumber":"4"` in a `GAME_STATE`, `"turnNumber":10` in `TURN_BEGAN`. Turn 0 states (the pregame) have no `activePlayerId`.
38. **Deltas never carry zones.** A `GAME_DELTA` patches the last state: `patch.state` (phase, step, priority player, clock), `patch.players` as `[{"i":0,"life":18}]`, and the whole `pendingAction`. It never has a card, a zone or a hand or library size. Full states come with every board change, so match detail and replays read zones only from full states.
39. **A full state can list a spell nowhere.** While a cost is being paid, the card that went onto the stack is in no zone: the hand is one short and the stack unchanged (04:573, with `PAY_MANA` pending). One state without a card does not mean the card left the game.
40. **A named `Hand -> Stack` zone change is the start of a cast, not a cast.** It comes before the cost is paid, and a cast the player takes back sends nothing more: no `SPELL_CAST`, no resolve, and the card is back in hand at the next state. Of the 23 named moves onto the stack in the fixture (21 from a hand, 2 Living End from exile), 21 are followed by a `SPELL_CAST`. The 2 that are not are casts taken back: the user's Talisman of Resilience in game 2 (04:572, `CANCEL` at 04:579) and the opponent's Force of Negation in game 3 (04:923). So the replay writes a cast only at `SPELL_CAST`. A taken-back opponent card is only identified: the user saw it, so the replay writes `identify` and the stored rows count it as seen, cast 0. That Force of Negation is a card known only from an event: no state ever lists it. Back in the hidden hand it gets a new hidden id, so a later cast of it names a new Forge id, and the old id can come back on another card: the replay takes the card named so in that hand for the new id (and drops the old one), and a state that shows the old id under another name gets a new object, not the named hand card.
41. **Forge sends a spell's effects before its `SPELL_RESOLVED`.** What a spell or ability does (a milled card, a land found, Living End's moves) arrives before the event that names it resolving (02:63 to 02:65). The replay writes `resolve` at the first event of that batch, so the effects take the resolving object as their cause.
42. **Cascade's looks and exiles arrive before their trigger resolves, across a full state.** The 21-card look and the moves to exile (02:368 onwards) come before the cascade trigger's `SPELL_RESOLVED`, which only follows the next full state. The replay writes those lines with cause `?`: looking past a full state for the resolve would write other spells' resolves before their costs are paid.
43. **Some events carry no card id and no `playerIndex`.** `SPELL_REMOVED_FROM_STACK`, `SHUFFLE` and `TOKEN_CREATED` (only "Token created") name no card. The player of a shuffle is only in its text (`"<name> shuffled their library"`), matched against the game's player names. A token's id comes from its `(created) -> Battlefield` zone change or the next full state.
44. **Forge names no card on a draw**, not even the user's own (`"a card: Library -> Hand"`). The replay reads the user's drawn card from the next full state; the opponent's stays hidden. No event says which card was the first draw, so Endstep games store no `first_draw`.
45. **A targeted player is named only in `targetDescription`.** In a stack entry's targets a player is id -1 with no owner. The entry's `targetDescription` (`[Player], [Subtlety (109), Oliphaunt (118)]`) is the only place the player is named. Targets are written only when a full state shows the stack entry.
46. **A draw and a play that reach one full state read as a library move.** When an opponent card is drawn and played with no full state between, and no event places it, the hand size is unchanged: the replay's state diff writes `new card ... in library` and a move from the library, not a hidden draw then a play from hand.
47. **Forge effect objects are not tracked, so their actions have no source.** Devourer of Destiny's upkeep effect sits in the command zone as an object with no types (trap 24). The replay has no object for it, so the card that effect exiles at upkeep has no `look` line before its exile.
48. **Forge's ability text carries card ids and notes.** `abilityDescription` holds card ids such as ` (78)`, a closing note such as `[Zone Changer: Hedge Maze (78)]`, and a `(Targeting: ...)` part that can name a player. The replay writer cuts each ` (digits)` that follows the name of the card the game's states or events give that id (a number after anything else, as in `discards a card (2)`, is rules text), the bracket note and the `(Targeting: ...)` part; reminder text in parentheses stays, and so does a player name inside Forge's own sentence (`Oliphaunt - Opponent searches ...`). One ability text in the fixture (Ugin's Labyrinth's imprint) contains the em dash character; the record keeps Forge's text, and the committed snapshots replace that character with a hyphen, because the repository keeps it out of every file.
49. **A state's board fields have their own shapes.** `stack` lists the top first (unit 04: Force of Negation at 0, Kozilek's Command at 1). `BLOCKERS_DECLARED.blockerAssignments` is an object from blocker id to attacker id (`{"16": 82}`), not a list. `counters` is an object. A non-creature has power and toughness 0/0. `GAME_STARTED` names who plays first in `playerIndex` and who chose in `tossPlayerIndex`.
50. **Forge sends the sideboard prompt again after the submit.** After the user's `SIDEBOARD_SUBMIT` (`promptVersion` 268 at 04:250, 401 at 04:669), the next `GAME_DELTA`s carry the same `CHOOSE_CARDS` prompt with a new `promptVersion` (270 and 271 at 04:251 to 04:253; 403 and 404 at 04:670 to 04:673) and `sideboardState.self: "SUBMITTED"`; before the submit it is `"EDITING"`. The options and their ids are unchanged. The fold keeps the prompt the submit answered together with the answer, so a later version does not drop it; only a new submit that matches the then-current version replaces it.
51. **Full states carry mana pool totals, and nothing more about mana.** Every player in a full state has `manaPool`, usually `{}`; 39 entries in the fixture's game socket states are not empty (such as `{"colorless":1}` at 02:101). No frame says which permanent made the mana or what spent it (`MANA_LOG` is text only), so the replay keeps `Omits "mana"`.
52. **A reveal into a library does not say who saw it.** `CARD_REVEALED` with `toZone` `Library` (the 21-card cascade look at 02:368) names the cards but not whether both players saw them, and its `playerIndex` is the viewer (trap 27). The replay writes each card as a `look` by the user, never as a public `reveal`, even when the effect (a cascade) showed it to both players.
53. **The game socket can stay open after the match ends** (issue #751). The extension closes a match unit when its game socket closes, so a socket Endstep keeps open held the last unit back: the match stayed live in MyMTGO and the popup kept "Recording 1 match". The end is a frame whose `matchScore.isMatchOver` is `true`: in the fixture the lobby socket's `GAME_OVER` (04:1144) and the `GAME_STATE` after it, while the game socket's own states never say so. The extension closes the match unit after such a frame when it comes on the unit's game socket (a state's `payload.matchScore` or a delta's `payload.patch.state.matchScore`) or on the lobby socket naming a `gameId` that game socket carried (`extension/src/capture/units.ts`). Frames after it (the ranked result) go to a session unit, and the `db:` ref (trap 17) joins them to the match.
54. **A repeated frame is the same kind, `seq` and `sequenceNumber`, not the same `seq`.** A refresh can send a game frame again, and the fold reads each one once. It keys a frame on its kind (state, delta or event), its envelope `seq` and, for an event, its `sequenceNumber`: a frame that differs in any of them is read, so a state and an event that happen to share a `seq` are both kept. A frame with no `seq` (the lobby's `GAME_OVER`) is always read. No restart of the envelope counter has been captured (it continues across a gateway move); if one happened, states and deltas that reuse a `seq` would still be dropped as repeats.
55. **The page fetches the match body again.** The fixture has seven `GET /api/matches/<id>` bodies for one match (01:72, 01:74, five in unit 03 after the gateway move). Only the first body of a match counts as activity: a later one (a reload, another tab opened on a finished match) must not move the match's last activity or keep a quiet match in progress. The match's fields still come from the last body.
56. **One `GAME_OUTCOME` per game.** The fixture has exactly one per game (04:239, 04:666, 04:1142), and the next game is named only by a state's `matchScore.gameNumber`. A second outcome for a game already decided is ignored, whatever it says: it never rewrites the winner, the end reason or the turn count, and never starts a game, since a game number comes only from `matchScore` (trap 7). An exact resend is a repeat frame anyway (trap 54).
57. **Flags can come as text or numbers.** Endstep sends some numbers as strings (trap 3), so the decoder reads a flag such as `isMatchOver` or `faceDown` as true for JSON `true`, the number 1 and the text `"true"` or `"1"`; anything else is false.
58. **A score can name more games than the match has.** `winsBySeat` is trusted only while its total fits `gamesPerMatch`. A Bo1 whose score adds up to three games is hostile input: the fold counts the decided games up to the limit instead.
59. **A match's units can sit far apart in a backlog.** Units are taken in `(started_at, counter)` order, a few per poll, and a long match's session and match units can fall into different polls. A fold reads the units its refs reach, so the tracker stores the refs of every unsynced unit before it folds any match (#676); otherwise the first poll would fold the match from part of its units and write a wrong match, deck and state until the rest arrived.
60. **A double-faced card keeps its id when it turns over.** A full state lists the card under the face it shows, so one card id can carry two names in one game (a transformed creature, a modal card played as its back face land). The fold counts each card id once, under the first name a state or event gave it, and the events that name it later (a land played as its back face) count on that row (#691).
61. **An activated card can be named only by its activation.** `ABILITY_ACTIVATED` names its card and id (`"Opponent activated Misty Rainforest"`, 04:376). The fixture's activated cards all show in a state too, but a card activated from a zone no state captured would otherwise make no row, so an activation is a sighting like a cast or a land play (#691).
62. **A discard comes twice: a named zone change, then `DISCARD_LOG`.** Each of the fixture's five discards (the opponent cycling Oliphaunt, Generous Ent and Curator of Mysteries, 02:147, 04:413, 04:493, 04:859, 04:1135) is a named `CARD_ZONE_CHANGE` `Hand -> Graveyard` with `zoneOwnerIndex`, then a `DISCARD_LOG` with the same `cardId`, `cardName` and the discarding player in `playerIndex` (`"Opponent discards Oliphaunt."`). The fold counts a discard from either, once per card id, from the seat's kept hand on (every discard when no keep was captured), and without needing a full state: the events name it. No discard of the user's own was captured, so whether Forge always sends both for the viewer is not known; reading either keeps the count when one is missing (#707).
63. **Three sources count a mulligan, and each can miss one.** `MULLIGAN` with `amount` (the redraw), the hands sent back (named in full states) and `HAND_SETTLED.mulligans`. A lost event or a lost state leaves one of them short, and none counts one too many, so the stored `games.local_mulligans` and `opp_mulligans` are the largest of them (the opponent's hands are hidden, so its count is the events or its settle), and the match page shows the larger of the hands it lists and that stored count, as Game Stats reads it. Likewise the starting hand size is `HAND_SETTLED.amount` (never above the opening hand) when that settle came after the opening hand was fixed, even when no state shows which card went to the bottom (#707).
64. **A match that ends on the clock is long, and its unit can pass 32 MiB.** Each player has a 25 minute bank (`clock.timeBankMs` 1500000), so a timeout match can run about 50 minutes. Full states and deltas grow late in a game (a delta carries the whole `pendingAction`), so the unit is far bigger than a normal match. The extension sends a unit over 32 MiB in parts (`deliver_part`, `deliver_end`) because Chrome caps one message at 64 MiB, and the helper and the app accept a capture up to `MAX_CAPTURE_BYTES` (512 MiB) (#660). Until then such a match waited in the extension with "too large" and never reached MyMTGO. Such a long match's Endstep source will likely compress to more than the cross-device sync blob limit (`COMPRESSED_PER_BLOB`, 2 MiB), and the sync rejects it cleanly, so it stays on the device that recorded it (expected, not yet measured on a real long capture).

Known limits of the capture (accepted, not bugs to fix without a new decision):

- **Frames are visible to the page.** Each captured frame travels from the page hook to the extension as a `window` message event, so the page's own listeners can see it (the standard MAIN to ISOLATED bridge).
- **Another extension can bypass the send hook.** If a different extension wraps `WebSocket` and returns another object, our `send` override never sees the user's outgoing frames.
- **A service-worker restart mid-match splits the match.** The live match unit closes and is delivered truncated, and the rest of that match's game frames go to session units. Session units are unclassified, so a spectated or bot remainder is sent too (the fold makes no match from it, but the unit stays stored: see below). No frame is lost, and the fold reads all units by their ids.
- **REST bodies are kept only when the content type is JSON.** A JSON endpoint served with another content type is not captured. A streamed body (event stream) is never buffered.
- **The match unit can classify unknown.** If `GET /api/matches/<id>` arrives before the game socket opens, the capture-time bot filter never fires and the unit is kept as unknown. The import decides.
- **Secret-named keys are stripped** unless the value is a boolean. Names match ignoring case, `_` and `-`: a fixed set (`token`, `ticket`, `cookie`, `password`, `email`, `jwt`, `apiKey`, `sessionId`, `csrf`, `xsrf` and a few more), plus any name ending in `token` or `ticket` (`authToken`, `gameTicket`). So a flag such as `isToken: true` survives, a card list under `tokens` survives (it does not end in `token`), and a real ticket does not.
- **Match REST bodies count only when they belong to the unit's game.** The page can fetch `GET /api/matches/<id>` for other matches while one runs, so classify uses a body only when its `forgeGameId` equals a `payload.gameId` in the unit's game socket frames. Anything else is ignored and the unit falls back to unknown (kept).
- **Units over 512 MiB wait in the extension.** They stay in IndexedDB with the status "too large" and are not delivered. Units from 32 MiB to 512 MiB go in parts (trap 64).
- **The Windows registry keys survive an app update, not every install.** An update through the app never runs the old uninstaller (Tauri's installer skips it in update mode), so the three keys stay. A double-clicked installer with the default "Uninstall before installing" runs the old uninstaller with `$UpdateMode` at 0 and removes them until MyMTGO next starts and registers again (`app/src/endstep/host.rs` `action_for`). A real uninstall removes them through the hook (`app/installer/hooks.nsh`). To verify on a Windows machine.
- **Browser coverage on Linux.** Flatpak browsers are unsupported (no native messaging by default). Snap Firefox is untested.
- **An extension update or reload keeps open tabs capturing.** After an install or update the browser does not run the declared content scripts in tabs that are already open, so their old relay is dead. The background script runs `relay.js` again in every open endstep.cc tab on `onInstalled` (reason `install` or `update`), on every background load and when endstep.cc access is granted again (`extension/src/background/reinject.ts`), and the page hook that was already running gets a live relay. Each relay leaves a probe, `__mymtgoRelay`, on the isolated world's global; a new relay installs only when no earlier one answers that it is alive (`extension/src/relay/install.ts`), so a tab has one live relay and frames are not doubled. Checked with unit tests only; the owner checklist has the real-browser check.
- **After an update, the old page hook keeps running in open tabs.** Only the relay is injected again, so a tab that was open before the update still runs the previous version's page hook (`extension/src/page/hook.ts`), and it feeds the new relay and background script until the tab reloads. A change to the shape of the hook's events must stay readable by the new background script, or those tabs lose frames until they reload.
- **A tab open before the first install needs one reload.** Only the relay is injected again. The page hook must run before Endstep's code opens its sockets, so a tab that was open before the extension existed has no hook until it is reloaded.
- **In Chrome, disabling and re-enabling the extension is handled.** `onInstalled` does not fire on enable, but the background script loads again, and every load runs `relay.js` in the open endstep.cc tabs, so they capture again without a reload (the relay guards against a double install).
- **Frames captured mid-game after an update go to a session unit.** The new background script does not know the game socket that opened before the update, so that socket's frames go to the tab's session unit, not a match unit. The session unit names the Forge game id (`game:` ref, trap 17), so the fold joins it to the match.
- **The page can see the hook's marker.** The page hook marks the page's `window` with a non-enumerable property, `__mymtgoEndstepHook`, so a second run does not wrap `WebSocket`, `fetch` and `XMLHttpRequest` twice. Endstep's own scripts can read it.
- **A capture the extension could not classify is stored even when it is a bot match.** The extension drops bot and spectated matches only when it knows the participants. An unknown unit is sent, and MyMTGO's import stores it in `endstep_captures` like any other. When the fold then finds a bot or no seat for the user, it makes no match, but the stored unit is not deleted. This is against spec section 2 ("not saved, not imported") and is issue #712.
- **Stored captures have no delete path yet** (issue #712). Switching Endstep off stops the import and keeps them; deleting a match does not remove them. Only removing MyMTGO's data folder does. `extension/PRIVACY.md` says so.
- **The store's Chrome extension id must be in the app before the listing is public.** The Chrome Web Store gives the upload its own id. The helper's manifest lists the Chrome ids it accepts (`CHROME_EXTENSION_IDS` in `crates/endstep-capture/src/registration.rs`), and Chrome refuses a native messaging connection from any other id, so the store extension says "MyMTGO helper not found" until an app version that lists the id is released.
- **The store Firefox build needs Firefox 140.** Its manifest declares `data_collection_permissions`, which Firefox honours from 140, so `strict_min_version` is 140.0 in the store build (the dev build keeps 128.0). Firefox 128 to 139 cannot install the store build.
